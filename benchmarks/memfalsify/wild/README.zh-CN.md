# MemFalsify 在真实仓库上的表现

[合成基准](../README.md) 检查的是已知的失败模式。这个基准问的是另一个问题：词法验证器在真实项目的 `CLAUDE.md` 或 `AGENTS.md` 里标记了一行，这个标记值得读吗？

`labels.jsonl` 里有 413 个标注过的配对，来自公开仓库的智能体文件：一条记忆，以及验证器拿来反驳它的那段来源。文件只有元数据和哈希（仓库、提交、记忆文件和行号、来源路径和行号、记忆和引文的 SHA-256、标注时的规则、标签、原因和文件类别）。除了文件名，这些项目的文字都不在本仓库里，所以脚本需要克隆。

## 运行

```bash
python benchmarks/memfalsify/wild/run.py --check                     # 检查标签格式，不需要克隆
python benchmarks/memfalsify/wild/run.py --clones DIR                # 先算标注配对，再跑完整审计
python benchmarks/memfalsify/wild/run.py --clones DIR --no-audit     # 只算标注配对，几秒钟
python benchmarks/memfalsify/wild/run.py --clones DIR --json OUT
```

`DIR` 里放浅克隆，目录名为 `<owner>__<name>`，提交与 `labels.jsonl` 一致。克隆是不可信的数据：脚本只读取它们的文件，不运行其中任何东西，连 git 都不运行；你也应该把它们放在本仓库之外，不要在里面运行解释器。某个提交上找不到原文的配对计为 unresolved，提交不一致的克隆会被列出。

对你手上的代码，它会报告：按标注时的规则，有多少标注配对仍被标记、其中多少是真的、丢掉了哪些真的；然后对同一批记忆文件跑完整审计，报告有多少被标记的配对没有标签。这些是还没人判断过的标记。CI 没有克隆，所以只检查格式，并在一个虚构的克隆上打分（`tests/test_wild_benchmark.py`）。

## 标签是怎么来的

所有标注都由 AI 模型完成，由这项工作的负责人复核，而负责人也是一个 AI 会话。没有人参与标注。读这些数字时请记住这一点。

1. 用这项工作之前的验证器审计 15 个项目的智能体文件，得到 1,371 个不重复的（记忆，来源）矛盾配对，来自其中 14 个项目：1,218 个来自“只有一边被否定”，83 个来自相反词，70 个来自数字不同。27 个智能体文件中有两个不在这些配对里：grafana 的 `AGENTS.md` 审计超时，ruff 的 `AGENTS.md` 在提取配对之后才跑完。
2. 样本包括全部相反词配对和全部数字配对，再加上否定配对，每个仓库最多 25 个，总数最多 260 个，顺序固定：共 413 对。
3. 两个模型各自独立标注每一对，先是 Claude，然后是 Codex（OpenAI），都读克隆里该行周围的来源，互相看不到对方的标签。`real` 表示记忆和来源对同一件事的说法不可能同时为真；其他都是 `not_real`，并附原因。
4. 两者在 413 对中有 2 对不一致，都是 Claude 判 `real`、Codex 判 `not_real`。裁决后两对都定为 `not_real`。

结果是 11 对真的，402 对不是。

标注之后，读取文字的方式变了（记忆和散文类证据的折行都会合并，缩写不再切断句子，片段不再算记忆），所以哈希改为指向现在读到的文字。413 对里，72 对指向包含原标注片段的更长记忆，26 对指向更长的证据文字，标签不变。19 对都是 `not_real`，指向的文字已经不算记忆（标签、表头、结束标签），带有 `claim_dropped`，按不再被标记计算。更长的记忆没有重新标注，所以按片段标注的配对现在代表它所在的整句。

规则是在这些仓库上调整的。另有一批仓库留作保留集，不在这些标签里。

## 它可能怎样误导

- **它不能说明召回率。** 只有旧验证器标记过的配对才被标注，所以“丢掉的真实配对”只统计这些配对里的损失。验证器从没标记过的过期内容不在其中。另外，这些数字逐对统计，而人读的是一条记忆。
- **真实配对少，又集中在一个仓库。** 11 对真实配对里有 9 对来自一个仓库里一个文件的默认值列表。几对的变化就会让精确率大幅波动，具名值规则也是看着这些配对设计的。
- **抽样。** 否定配对只抽了 1,218 个中的 260 个，其他规则是全量标注。样本上的精确率偏高，因为假标记主要来自否定。脚本同时打印按比例换算的数字，引用时请用那个数字。
- **新标记没有标签。** 现在的规则会标记旧规则没标记过的配对，比如 `max_steps: int = 500`。所以脚本会打印没有标签的被标记配对数量。这些配对在这项工作中被读过，但没有标注。
- **标签里的运气。** 有些真实配对是碰巧对的：记忆确实过期了，但引用的来源并没有说明这一点（比如引用的是紧挨着真正相关设置的另一个设置）。把这些配对判“对”的验证器并不更好。调整规则时读过每一行的原因，这样的配对如果丢了，下面会列出。
- **两个标注者可能有相同的盲区。** 两个模型在 413 对里 411 对一致，不等于 411 对都正确。
- **仓库会变。** 这是标注时那个提交的快照，当时过期的内容现在可能已经修好了。

## 结果

测量于 2026-11-05，规则见[规则说明](../../../docs/lexical-rules.zh-CN.md)。

| | 之前 | 现在 |
|---|---|---|
| 完整审计中被标记的配对 | 1,719 | 47（下降 97.3%） |
| 完整审计中被标记的记忆 | 794 | 29 |
| 标签取自的 1,371 对中仍被标记的 | 1,371 | 24（下降 98.2%） |
| 标注样本中被标记的 | 413 | 16 |
| 保留的真实配对 | 11 中的 11 | 11 中的 9 |
| 标注样本上的精确率 | 0.03 | 0.56 |
| 按否定抽样比例换算的精确率 | 0.01 | 0.33 |

按标注时的规则，现在的情况：

| 标注时的规则 | 标注数 | 真实 | 现在被标记 | 保留的真实 | 保留的非真实 | 精确率 |
|---|---|---|---|---|---|---|
| negation | 260 | 0 | 3 | 0 | 3 | 0.00 |
| numbers | 70 | 10 | 9 | 8 | 1 | 0.89 |
| opposing | 83 | 1 | 4 | 1 | 3 | 0.25 |
| all | 413 | 11 | 16 | 9 | 7 | 0.56 |

丢掉的两个真实配对，引用的来源本身都没有显示问题：一个引用的是紧挨着真正不一致设置的另一个设置（这条记忆仍然被正确的那一行标记），一个引用的是列表项，说明它们已被移除的标题在更早的一行（这条记忆仍然被另一行标记）。每个真实配对对应的记忆行都仍然被标记。

完整审计覆盖 15 个仓库的 27 个智能体文件，每个文件都对照自己的仓库，每条记忆最多列出三段证据，前后一致。`run.py` 只审计含有标注配对的 18 个文件，所以它自己的计数更低。这项工作之前的报告里有 1,719 对和 794 条被标记的记忆。它们来自 27 个文件中的 26 个：grafana 的 `AGENTS.md` 当时审计超时，现在它没有增加标记。标签取自的 1,371 对更少，是因为提取时 ruff 的 `AGENTS.md` 还没跑完，所以少了它的 368 对。现在被标记的 47 对里，15 对有标签（8 对为真：有两行真实标注原本标在同一句话的两个片段上，现在指向同一对），32 对没有：8 对在原来的 1,371 对之中（其中一对的引文后来和它的折行合并了），24 对是新的。按理由统计：`same setting` 19、`same subject` 19、`set differently` 3、`opposing terms` 3、`different values` 2、移除 1。新配对读过但没有标注。其中大多数 `same setting` 指向的是记忆与之不一致的声明（`max_failures: int = 5`），这正是旧规则漏掉的召回，它们没有计入上面的 9 对真实配对。

对这些规则的一次审查，找回了第一轮按标签调整时拿掉的几样东西：短陈述和它的反面，以 `Do not` 开头的行和几乎相反的那一行，以及 `tests/`、`spec/`、`testing/`、`e2e/` 下的文档。在这些仓库上，代价是多了一个标记和两个内部冲突，读下来都不是真的：`no network calls allowed` 对 `Network call blocking`，来源是 `testing/` 下的一份文档；以及 mem0 同一文件的两个副本里，“不要做”列表中的一项 `Commit .env files, API keys, or credentials.` 对 `Never commit secrets`。它也去掉了三个 `same setting` 标记：在代码里，调用处的 `optimizeDeps: { noDiscovery: true }` 只是一个对象的字段，不是声明的值。标注表和合成用例的分数没有变。

把折行的证据读成一整句有得有失。它多标记了一行（不是真的），在真实配对很少的样本上让精确率降了 0.04。换来的是：记忆里折行、文档里也折行的同一句话现在能对上。在改动读取方式前后都审计过的 25 个智能体文件上（grafana 的两个文件在改动前超时了），记忆从 4,463 条变成 3,704 条，`NO EVIDENCE` 从 3,474 变成 2,966，`POSSIBLE SUPPORT` 从 946 变成 696，`POSSIBLE COUNTEREVIDENCE` 从 43 变成 42。失去的支持大多是碰巧匹配上的片段（`get closed.`）；这部分标签说明不了什么。

否定规则保留下来，是因为合成用例里会有“周五绝不允许部署”这样的陈述，它能找到；但在这些仓库上，它在抽样的 260 对中没有一对是真的，它仍然给出的 19 个标记读下来也没有一个是真的。在这里它没有达到可用的精确率。请把 `same subject, but only one side is negated` 当作弱信号；它在报告里排在最后。
